# Content Model

The database schema, why it is shaped this way, and where each piece surfaces on the site.

- Schema: [`supabase/migrations/0001_init.sql`](../supabase/migrations/0001_init.sql)
- TypeScript mirror: [`src/content/types.ts`](../src/content/types.ts)
- Seed data: [`supabase/seed.sql`](../supabase/seed.sql), generated by `npm run content:seed`

---

## The resolution rule

```
component  →  src/content/resolve.ts  →  Supabase (if configured AND reachable)
                                      →  src/content/*.ts   (always, as fallback)
```

Supabase reads have a **2.5-second timeout** and never throw. A CMS outage degrades the site to
last-known-good content; it does not take a restaurant's website offline.

This is also why the repository clones and runs with zero configuration, and why the static modules
double as seed data — the owner never re-enters content that was already captured.

## Tables

### `site_settings`

Singleton (`id = 'default'`) holding a `jsonb` payload that **partially overrides**
`src/content/site.ts`. Only keys present in the payload override the static defaults, so a partial
edit cannot blank out the address.

Surfaces in: the footer, `/visit`, the `Restaurant` JSON-LD, every `tel:` link.

### `announcements`

| Column | Note |
|---|---|
| `message` | 1–240 characters, enforced |
| `href` / `link_label` | Constrained so both are set or neither is |
| `starts_at` / `ends_at` | Optional window; `ends_at > starts_at` enforced |
| `enabled` | Defaults to **false** |
| `tone` | `default` (orange) or `night` (espresso) |

Ships disabled. The restaurant references a "$1 Taco Deal" and a lunch deal but publishes terms for
neither, so the bar is built and empty rather than filled with an invented offer.

### `menus` → `menu_categories` → `menu_items` → `menu_modifiers`

Four levels, each with `sort`, so ordering is data rather than array position.

**`price_cents` is nullable on purpose.** `NULL` means "not published" and renders as `price_note`
("Ask your server") — never `$0`, never a silently missing row. A check constraint requires one or
the other, so an unpriced item cannot render blank:

```sql
constraint menu_items_price_or_note check (price_cents is not null or price_note is not null)
```

Nine items are currently unpriced. The admin dashboard counts them as a warning on every load. See
[`CONTENT-QUESTIONS.md`](./CONTENT-QUESTIONS.md) §3.

`menu_modifiers.price_cents` is also nullable: a modifier with no price is a *choice* (which meat),
one with a price is an *upcharge*. The two render differently.

### `event_series` and `event_occurrences` — the important one

**`event_series` has no date column.** Not "usually empty" — the column does not exist.

| `event_series` | `event_occurrences` |
|---|---|
| `cadence` (`weekly:5`), `start_minutes`, `end_minutes` | `starts_at`, `ends_at` — actual timestamps |
| Age, music, ticket URL, price, artwork | Per-night status and price overrides |

Ordinary recurring dates are **generated at read time** by `src/lib/events.ts` for a rolling
26-week window. The `event_occurrences` table exists only for explicit overrides — a cancelled
night, a guest DJ, a sold-out date.

Consequences:

1. A recurring series **cannot** display a stale date, because it has no date to display.
2. The calendar never runs out, and nobody maintains 21 rows by hand.
3. Artwork is composited *under* live HTML date text, never read for the date. The asset checker
   fails the build if series artwork is tagged `containsText: 'date'`.
4. `check (end_minutes > start_minutes)` and `check (ends_at > starts_at)` make it impossible to
   publish an event that ends before it starts.

Times are stored as minutes from midnight in the venue's local wall clock. `end_minutes` may exceed
1440, which is how a 10pm–2am night is expressed. `venueLocalIso()` resolves the correct
America/Chicago offset per date, so a CST→CDT transition never shifts a 10pm door to 9pm.

### `catering_packages` and `catering_items`

Package `includes` is a `text[]` rather than a join table — these are display lines, not entities
anything else references. Prices came from the Toast catering menu.

### `page_sections` and `page_seo`

`page_sections.variant` is constrained to five approved layouts:

```sql
check (variant in ('editorial-left', 'editorial-right', 'stagger', 'band', 'plain'))
```

This is the editing boundary. An editor may change *what a section says* and pick from approved
compositions. They cannot set a font, a colour, a spacing value, or write CSS or raw HTML — so the
art direction survives contact with day-to-day editing.

`page_seo` enforces sensible lengths (`title` 10–70, `description` 50–320) at the database level, so
a truncated snippet cannot be saved.

### `media_assets`

Mirrors `src/content/assets.ts` so the admin can *show* what exists. It is read-only in the UI:
uploading directly would bypass the per-slot geometry and focal points that keep crops correct on
phones. `/admin/media` tells the manager what to send instead.

### `inquiries`

RLS here is deliberately asymmetric:

- `anon` and `authenticated` may **insert** (the public forms).
- Only signed-in staff may **select** or **update**.
- There is **no delete policy at all** — enquiries are business records.

### `profiles`, `audit_log`

`profiles.role` is the sole source of authorization. `audit_log` records every insert/update/delete
on every editable table with the actor and a JSON diff, via a trigger.

The `on_auth_user_created` trigger assigns `editor` — the least-privileged role — to every new
signup. Elevation is a deliberate act by an owner or admin.

## Authorization

Three independent layers, in order of authority:

1. **Postgres RLS** — the real boundary. Policies are keyed on `public.current_role()`, a
   `SECURITY DEFINER` function so a user can read their own role without a recursive policy.
2. **Server-side checks** — every mutation calls `requireRole()`, which *throws* rather than
   returning a flag, so a forgotten check cannot fall through to a write.
3. **Middleware** — bounces anonymous visitors from `/admin`. Convenience only.

Hiding a button in the UI is none of these. `/admin/settings` demonstrates the pattern: an editor
who navigates to it directly gets a server-rendered refusal, not a blank page.

## Caching and revalidation

| Route | Strategy | Why |
|---|---|---|
| `/`, `/menu*`, `/catering`, `/visit` | `revalidate = 3600` | Content changes rarely; the open/closed state changes hourly |
| `/events`, `/events/[slug]` | `revalidate = 300` | An event that has just ended must drop off the list promptly |
| `/admin/*` | `force-dynamic` | Always current, never cached |

Admin mutations call `revalidatePath()` for the affected routes, so an edit appears publicly within
one request rather than needing a redeploy.

## Migrations

`supabase/migrations/` is applied in filename order. Never edit an applied migration — add a new
one. `supabase/seed.sql` is **generated**; edit `src/content/*.ts` and re-run `npm run content:seed`.

Seed statements are upserts keyed on the primary key, so re-seeding a database the owner has already
edited overwrites the seeded rows and leaves anything they added alone.
